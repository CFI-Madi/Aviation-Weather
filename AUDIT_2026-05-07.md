## 1. Diagrams (the priority issue)

`js/diagrams.js` (2113 lines) contains ~30 distinct hand-coded SVGs plus 8 PROCESS_DIAGRAMS that already use FAA PNGs from `img/awh/`. The PROCESS_DIAGRAMS are fine — concern is the SVGs.

### Top 5 SVGs to replace first (factual errors)

1. **`coldFrontCrossSectionSVG`** — ❌ **Wrong**. The cold-air polygon (`points="0,185 300,185 0,22"`) fills the upper-left of the canvas, putting cold air at ~30,000 ft on the left edge. FAA Fig 11-6 shows cold air as a low wedge with warm air *above* at all altitudes — this SVG inverts that. The CB ellipses sit at ~22,000 ft (too low — should reach the tropopause). PROCESS_DIAGRAMS already uses FAA `frontal_lifting_02.png` for this exact concept, so this redundant SVG can simply be deleted.
2. **`mountainWave`** — ⚠️ Misleading geometry. Rotor placed adjacent to the peak instead of downwind under the first lee wave; lenticulars sit just above ridge line. Real mountain-wave lenticulars form well above ridge height (often FL250+) with the rotor downwind. PROCESS_DIAGRAMS already has FAA Fig 16-13/16-14 — reuse them.
3. **`cloudGallerySVG`** — 🤷 Stylized to the point of uselessness for ID. Cb thumbnail has no anvil; Cu/Sc/Ac thumbnails not visually distinguishable. Replace with FAA cloud photo plates (Ch 9). Text descriptions are accurate; only the visuals fail.
4. **`jetStreamSVG`** — ⚠️ CAT ellipses centered on the jet rather than offset to the cyclonic (poleward/cold) side. Jet-streak quadrants drawn as left/right blocks, not the four quadrants the (correct) explanation text describes. Visual contradicts text.
5. **`turbulenceSources`** — ⚠️ Mountain doesn't reach the CAT layer; CB cloud doesn't either; "inversion" is just a free-floating dashed line. Composition fails to teach where each turbulence type lives in the vertical column.

### Top 5+ SVGs that earn their keep (do NOT replace with FAA rasters)

1. **`densityAltCalc`** — Live PA + OAT slider with real-time DA output. Better intuition-builder than any static FAA chart.
2. **`waveCycloneSVG`** (5-stage tabbed) — Animated stage progression with correct front symbology. FAA shows snapshots; this teaches the time evolution.
3. **`microburstApproach`** (4-phase) — The phase-by-phase walk through "headwind-increase trap → downdraft → tailwind collapse" emerges from the animation in a way no static figure can match.
4. **`icingSeverityCalc` / `fogFormationCalc` / `renderFlightCategoryCalc`** — Three calculators with no FAA equivalent. Pure pedagogical wins.
5. **`renderMetarDecoder` / `renderTafDecoder` / `renderPirepDecoder` / `renderDecodePractice`** — Tap-to-decode token interactions are dramatically better than reading FAA Fig 24-1 callouts.

Bonus: **`lapseRateGraph`** (interactive ELR slider) — physics correct, no FAA interactive equivalent.

### Other diagrams flagged (lesser severity)

- **`atmosphereSVG`** — ⚠️ Layer thicknesses not to scale (acceptable pedagogically; flag only if you want strict proportions).
- **`windForcesSVG`** — ⚠️ Geometry doesn't make clear that Coriolis equals & opposes PGF in steady state. Easy to misread.
- **`frontsSVG`** — ✅ Stationary/occluded symbology drawn correctly. Keep.
- **`pressureSystemsSVG`** — 🤷 Card layout, no isobars or rotation arrows. FAA has actual H/L isobar diagrams (Ch 7) that would teach better.
- **`cbIngredients`** — Three separate triangles imply independence; the "ingredient triangle" metaphor in FAA Fig 22-1 is one triangle with three sides. Already covered by PROCESS_DIAGRAMS.
- **`cbLifecycle`** mature stage — anvil drawn separated from the cumulonimbus body. Already covered by PROCESS_DIAGRAMS.
- **`renderAdvisoryHierarchy`** — ⚠️ Pyramid metaphor implies strict priority ranking, but Convective SIGMET / SIGMET / AIRMET / CWA have different *domains*, not strictly different priority levels. Keep but consider redesign as four parallel cards rather than a pyramid.
- **`iceTypes` / `inversionTypesSVG` / `fogTypes`** — All 🤷 stylized cards with no physical depiction. FAA has airfoil-with-ice and sounding-curve diagrams that teach better.

A full table of all 30+ diagrams with concept/verdict/FAA-equivalent is held in the dispatched-agent output if needed.

## 2. Content accuracy

### Numerical errors / wrong physics (fix list)

- **Lightning frequency**: 40,000/day → should be ~8,000,000/day. (m6 s6_4) — flagged above.
- **DA formula in °F**: should be °C. (m2 s2_3, q_m2_4) — flagged above.
- **dBZ thresholds**: m14 s14_1 uses `<26 / 26-40 / 41-50 / 50+`. FAA-H-8083-28A Table 24-1: `<30 / 30-40 / 40-50 / >50`.
- **Radar beam height at 200 NM**: m14 says "~25,000 ft AGL"; standard 0.5° elevation gives ~19,000 ft.
- **BR (mist) visibility range**: m9 s9_1 and q_m9_5 say "5/8 to 7 SM". Actual: 5/8 to 6 SM.
- **Convective SIGMET issuance**: m15 s15_1 says "H+55 and H+25". Convective SIGMETs go out at H+55 with WSTs as needed; H+25 belongs to non-convective SIGMET handling.
- **Tornado source statistics**: m6 s6_3 says supercells produce "~25%" and squall lines produce "~25%" — adds to 50%, missing the rest. Reality: supercells produce the majority (>75%) of *significant* (EF2+) tornadoes; QLCS produces many weak ones. Reframe.
- **CB avoidance distance**: m6 s6_5 softens to "20 NM is a conservative training answer". AC 00-24C / AIM 7-1-29 makes 20 NM a hard recommendation for severe/extreme intensity. Don't soften.
- **CAT altitude floor**: m8 s8_3 states "above 15,000 ft". AIM 7-1-22 has no strict floor. Reword.
- **mA "Maritime Arctic" air mass code**: m5 s5_1 lists this; standard FAA scheme uses **cA (continental Arctic)**. mA is not standard.
- **Friction-layer altitude inconsistency**: m3 s3_2 says "~3,000 ft AGL"; q_m3_10 says "~2,000 ft". Pick one (FAA standard ≈ 2,000 ft over flat terrain).
- **Cloud coverage thresholds**: m11 never explicitly defines FEW/SCT/BKN/OVC eighths. Add the table.
- **High-to-low conflation**: Throughout m2, the *pressure-based* "high to low look out below" mnemonic and the *temperature-based* cold-temperature error are mixed as if they were one rule. Same operational outcome, different physics — separate them.

### Style / standards violations

- **Aircraft-specific content**: PA-28-140 / PA-28-181 / C172S referenced explicitly in q_m2_12 and across m6, m7, m8, m9, m10, m17, m20 quiz items. The standard you stated is aircraft-agnostic — these need rewriting.
- **m7 s7_5 (carb ice)**: stripped of useful FAA content (specific temp/RH ranges) under the "aircraft-specific" caveat. Better to keep the FAA's general carb-ice envelope and note that engines vary.

### Garbled HTML / Unicode (already in the must-fix list)

m3/s3_3, m3/s3_4, m5/s5_3, m9/s9_4, m15/s15_5, m1a/s1a_2 — sections opening mid-sentence and `???` characters where emoji/special chars used to be. Looks like an aggressive find-replace went too far at some point.

## 4. NTSB case studies & references

- **15 cases total (cs1–cs15).** Only **3 are verified with external NTSB links** (cs1 Kennedy/PA-32, cs4 Delta 191/L-1011, cs12 American Eagle 4184/ATR-72). The other 12 are pattern-based scenarios marked `verified:false`, with a yellow "TRAINING SCENARIO" banner.
- **All 3 NTSB links are live** (verified — NYC99MA178 docket, DCA85AA031 final report, DCA95MA001 final report). Concept-match for all 5 cases I spot-checked is faithful to the real event.
- **The "three-category color-coding" framing in the briefing does not match the implementation.** The data model has only `ntsbUrl` + optional `ntsbSourceType` (free string). There is no CAROL search link type, no safety-alert link type, and no per-type color in [js/screens.js:1560-1624](js/screens.js:1560). Either:
  - (a) Build it: extend the schema to support multiple typed links per case (`'docket' | 'final_report' | 'carol' | 'safety_alert'`) with distinct color tokens, OR
  - (b) Drop the framing: accept that the app currently has one link type, and the audit need is just "verify the 3 live links stay live" — which they do.
- **Schema fragility**: `ntsbSourceType` is a free string; rendering branches on `.includes("docket")`. A typo silently flips the wrong button label. Recommend an enum.
- **Scenario coverage opportunity**: cs2/cs3/cs5/cs6/cs8/cs9/cs10/cs11/cs13/cs14/cs15 are clearly modeled on real archetypes; several could be linked to specific NTSB dockets via CAROL search and promoted to `verified:true`.

## 5. Navigation, structure, UX

### Routing (mostly solid)

- `js/router.js` handles bad URLs gracefully — unknown routes/IDs fall back to `dashboard` or the parent list. `_skipHash` guard prevents the hashchange/navigate loop.
- **Bug:** `metar_live` route is dead (see #0).
- **Cosmetic:** on `quiz`, `lesson`, `checkride_results` screens, no bottom-nav button is highlighted (the secondary list at [router.js:69](js/router.js:69) is incomplete).

### Onboarding & resume

- `Onboarding` is fully defined ([js/screens.js:1818-1938](js/screens.js:1818)) with disclaimer → level → start. Persists `firstLaunchSeen` and `learnerLevel`. **`learnerLevel` is set but never read anywhere downstream** — the personalization claim is empty.
- "Resume" on dashboard is coherent.
- **Quiz-in-progress recovery is half-wired**: `quizInProgress` is saved on every quiz advance, but the router intentionally maps `#/quiz/<id>` → `#/lesson/<id>`, so a full page refresh never lands on the quiz screen. The resume prompt only appears when the user clicks the Quiz button on the lesson screen after navigating away. Either commit to persistent quiz state (and add `#/quiz/<id>` to the router) or delete `quizInProgress`.

### Visual / typography / a11y

- **Typography mismatch with stated brand standard** — your briefing says *Bebas Neue / IBM Plex Sans / IBM Plex Mono*. The deployed app loads *Nunito + Space Mono + DM Sans* ([index.html:10](index.html:10)) and these are hardcoded as inline `font-family` in **202 places** across `screens.js`. Either the brand standard has drifted or the implementation has drifted — needs your call. (Recommend: pick one, then refactor to CSS variables — `--font-display`, `--font-body`, `--font-mono` — so future swaps are one edit, not 200.)
- **"PASS" / "FAIL" / "REVIEW" / "OK" / "Done" / "TOP" appear as bare text** at [js/screens.js:914, 1015, 1130, 1132, 1660-1661](js/screens.js:914) where the surrounding code clearly intended emojis. Looks like an emoji-strip pass overshot.
- Focus rings & keyboard nav: solid (`:focus-visible` + `tabindex="0"` + Enter/Space handlers on cards).
- ARIA: sparse but the basics are covered.

### Mobile / responsive

- Single `@media` query in the entire stylesheet (`max-width:768px` on the wrapper). No tighter breakpoints.
- Several `grid-template-columns:1fr 1fr 1fr` blocks in screens.js will get cramped at <360px (won't break, just tight).
- `body{overflow-x:hidden}` masks layout bugs rather than fixing them — common pattern, just be aware.

- `index.html` loads `js/data/*` then `js/*` then `js/app.js`. **No build step, no Python helper scripts, no generators.** Edits to `js/*.js` reach production unchanged. The "edits to the wrong file" family-wide bug *does not apply* to this app — good news.

### Dead code / orphans

- **`pressure_altimetry_comic.html`** (61 KB at repo root) — zero references anywhere. Stray experiment. Move out of repo or `.gitignore`.
- **Empty directories**: `content/modules/`, `content/case_studies/`, `legal/`. All inventory data is inlined in `js/data/`. Either delete the empty dirs or migrate data into them (the latter would also help with diffability — `modules.js` is 3674 lines).

- `js/screens.js` is **1941 lines** with **200+ inline `font-family`** declarations and dozens of inline-styled card scaffolds. A `_card(title, body, opts)` helper plus a small CSS class set (`.card-title-lg`, `.card-action-btn`) would cut hundreds of lines and unblock a clean typography refactor.

### Service worker / caching

- `sw.js` shell list covers all 11 scripts in `index.html`. ✓
